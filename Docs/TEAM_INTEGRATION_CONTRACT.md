# ELDIA Team Integration Contract

Status: verified against `feat/hari-core` commit `11f1ba8`.

This document describes existing contracts and responsibilities for teammate
branches. It is an integration reference, not a proposal to duplicate or
replace current gameplay systems.

## Project and scene

- Unity: `6000.6.6f1`
- Main test scene: `Assets/ELDIA/Scenes/PlayerTest.unity`
- Runtime bootstrap: `Assets/ELDIA/Scripts/Core/PlayerTestArena.cs`
- Scene objects are generated by `PlayerTestArena.Awake`; most gameplay objects
  are not serialized individually in the scene.
- Scene is enabled in `ProjectSettings/EditorBuildSettings.asset`.
- Input backend: Legacy Input Manager (`activeInputHandler: 0`).

## Combat and boss integration

### `DamageRequest`

Path: `Assets/ELDIA/Scripts/Gameplay/Shared/DamageTypes.cs`

```csharp
[Serializable]
public readonly struct DamageRequest
{
    public int Amount { get; }
    public GameObject Source { get; }
    public Vector2 HitPoint { get; }
    public Vector2 Direction { get; }

    public DamageRequest(
        int amount,
        GameObject source = null,
        Vector2 hitPoint = default,
        Vector2 direction = default);
}
```

`Amount` is requested damage. Target implementations validate it when damage
is applied. `Source`, `HitPoint`, and `Direction` are optional context.

### `DamageResult`

```csharp
[Serializable]
public readonly struct DamageResult
{
    public bool WasApplied { get; }
    public int AmountApplied { get; }
    public bool TargetDefeated { get; }

    public DamageResult(bool wasApplied, int amountApplied, bool targetDefeated);

    public static DamageResult NotApplied { get; }
}
```

`AmountApplied` is actual health lost, not requested damage. Rejected damage
returns `DamageResult.NotApplied`.

### `IDamageable`

Path: `Assets/ELDIA/Scripts/Gameplay/Shared/HealthContracts.cs`

```csharp
public interface IDamageable
{
    bool CanReceiveDamage { get; }
    DamageResult ReceiveDamage(DamageRequest request);
}
```

Combat entities that can receive attacks should implement this contract rather
than adding another damage interface.

### `IHealth`

```csharp
public interface IHealth
{
    int CurrentHealth { get; }
    int MaxHealth { get; }
    bool IsDefeated { get; }

    event Action<HealthChangedEvent> HealthChanged;
    event Action<EntityDefeatedEvent> Defeated;
}
```

Events:

```csharp
public readonly struct HealthChangedEvent
{
    public int CurrentHealth { get; }
    public int MaxHealth { get; }
    public int Delta { get; }
}
```

```csharp
public readonly struct EntityDefeatedEvent
{
    public GameObject Entity { get; }
    public GameObject Source { get; }
}
```

`EntityDefeatedEvent` is generic for all health-bearing entities. It is not a
boss event.

### Existing health implementation

Path: `Assets/ELDIA/Scripts/Gameplay/Health/HealthComponent.cs`

Responsibilities:

- Implements `IHealth` and `IDamageable`.
- Owns current/max health and damage validation.
- Emits `HealthChanged` when health changes.
- Emits generic `Defeated` once when health reaches zero.
- Rejects damage after defeat.
- `Heal` rejects healing after defeat.
- `SetMaxHealth(int)` clamps max/current values.
- `ResetHealth()` restores max health and clears defeated state.

Do not implement a second health store for an existing entity.

### Existing player attack

Path: `Assets/ELDIA/Scripts/Gameplay/Combat/PlayerAttack.cs`

Responsibilities:

- Reads Legacy Input Manager button `Fire1`.
- Default serialized values:
  - `attackDamage = 25`
  - `attackRange = 1.5`
  - `attackInputName = "Fire1"`
  - `attackCooldown = 0.3`
  - `targetLayers = ~0`
- Uses `Physics2D.OverlapBoxAll` in current facing direction.
- Sends `DamageRequest` to `IDamageable` targets.
- Prevents duplicate hits per attack.
- Creates temporary hit feedback.

Input mapping in `ProjectSettings/InputManager.asset` currently maps `Fire1`
to `left ctrl` and mouse button 0. The script comment also mentions J, but
current project settings should be treated as authoritative.

### Existing ordinary enemy

Path: `Assets/ELDIA/Scripts/Gameplay/Combat/BasicEnemy.cs`

Responsibilities:

- Implements `IDamageable`.
- Uses `HealthComponent` for health.
- Stationary test target; no AI movement.
- Fades and deactivates after generic entity defeat.

### Existing boss

Path: `Assets/ELDIA/Scripts/Gameplay/Boss/BasicBoss.cs`

Responsibilities:

- Implements `IBoss` and `IDamageable`.
- Forwards damage to `HealthComponent`.
- Boss ID: `district-warden`.
- Default configured max health: `150`.
- Emits one `BossDefeatedEvent` after observing generic health defeat.
- Owns boss-specific hit/defeat visuals.

Boss event:

```csharp
public readonly struct BossDefeatedEvent
{
    public string BossId { get; }

```

Use `IBoss.Defeated` for boss lifecycle integration. Do not reinterpret
`IHealth.Defeated` as boss-specific.

### Mission coordinator

Path: `Assets/ELDIA/Scripts/Gameplay/Mission/MissionCoordinator.cs`

Responsibilities:

- Implements `IGameState` and `IVictoryState`.
- Configures from `IObjective` and `IBoss`.
- Starts `Intro -> Playing`.
- Subscribes to objective completion and boss defeat.
- Derives authoritative prerequisites from `IObjective.IsCompleted` and
  `IBoss.IsDefeated`.
- Requires both prerequisites for `Playing -> Victory`.
- Emits `VictoryTriggered` once.
- Does not load scenes or own restart policy.

Public configuration and state:

```csharp
public void Configure(IObjective missionObjective, IBoss missionBoss);
public GameState CurrentState { get; }
public bool HasWon { get; }
public bool ObjectiveCompleted { get; }
public bool BossDefeated { get; }
public event Action<GameStateChangedEvent> StateChanged;
public event Action<VictoryEvent> VictoryTriggered;
```

The existing boolean parameters on `TryTriggerVictory` are retained for the
shared interface, but `MissionCoordinator` does not treat caller-supplied
booleans as authoritative.

## Player movement and level integration

### Player controller

Path: `Assets/ELDIA/Scripts/Player/PlayerController2D.cs`

Verified values:

```text
moveSpeed: 5 units/second
gravityScale: 0
freezeRotation: true
collisionDetectionMode: Continuous
```

Movement calculation:

```csharp
movementInput = NormalizeInput(new Vector2(
    Input.GetAxisRaw("Horizontal"),
    Input.GetAxisRaw("Vertical")));

body.MovePosition(body.position + movementInput * moveSpeed * Time.fixedDeltaTime);
```

Diagonal input is normalized when magnitude exceeds `1`, so diagonal speed is
approximately capped at the same configured speed as cardinal movement.

There is no jump implementation, jump force, gravity-driven vertical motion,
variable-height behavior, acceleration, or deceleration. Consequently, no jump
height calculation applies.

### Player collision setup

`PlayerTestArena` creates the player with:

```csharp
Rigidbody2D
BoxCollider2D
PlayerController2D
```

The player collider uses Unity's default `BoxCollider2D` settings because no
size or offset is assigned in code. Unity therefore uses the component default
size/offset; exact runtime dimensions should be confirmed in Inspector or
Play Mode.

`PlayerController2D` requires both `Rigidbody2D` and `BoxCollider2D`.
Rigidbody configuration is applied in `Awake()` as listed above.

### Ground and collision assumptions

There is no ground detection because this is top-down movement, not platformer
movement. Arena walls and obstacles receive `BoxCollider2D`; player movement is
blocked by 2D physics collision.

The generated arena creates:

```text
North Wall:   (0, 5.3), size (18, 0.6)
South Wall:   (0, -5.3), size (18, 0.6)
East Wall:    (9.3, 0), size (0.6, 10)
West Wall:    (-9.3, 0), size (0.6, 10)
Center Obstacle: (2.5, 0.7), size (2.5, 0.6)
South Obstacle: (-2.5, -1.2), size (0.6, 2.4)
```

### Layers and sorting

`ProjectSettings/TagManager.asset` currently defines only default named layers:

```text
Default
TransparentFX
Ignore Raycast
Water
UI
```

No custom gameplay layers are defined. Runtime gameplay objects use layer `0`
(Default). `PlayerAttack.targetLayers` defaults to `~0`, so it queries all
layers and filters by `IDamageable` component.

Sorting layers currently contain only:

```text
Default
```

Runtime render ordering uses per-renderer `sortingOrder` values:

```text
Background: -10
Arena Floor: -5
Most gameplay sprites: 0
Hit effects: 10
```

Physics 2D collision matrix is all `f`, meaning all layer pairs are enabled in
the current project settings. Runtime colliders therefore rely on default
layer interaction; no custom layer collision policy exists yet.

## Scene ownership and integration risks

- `PlayerTestArena` owns runtime generation for the current test scene.
- Do not add duplicate player, boss, objective, camera, or mission systems to
  the same scene.
- The camera is generated as `Main Camera` under the arena-owned
  `Generated Arena` root.
- Runtime cleanup destroys only the arena-owned generated root and its owned
  camera; it does not search globally for or delete an unrelated camera.
- `PlayerController2D.Configure(Transform)` provides explicit, type-safe facing
  indicator wiring.
- Unity's normal delayed `Destroy()` lifecycle is retained; runtime code does
  not use `DestroyImmediate()`.
- The scene is a test harness, not a final level-authoring workflow.

## Verified vs unresolved

Verified from source/settings:

- Existing contract declarations and event signatures.
- Player speed, Rigidbody2D configuration, input mappings, and no-jump design.
- Runtime-generated arena object responsibilities.
- Default layers, sorting layers, and all-enabled 2D collision matrix.
- Scene path and build-settings inclusion.

Requires Play Mode/Inspector confirmation:

- Effective runtime collider bounds after generated setup.
- Repeated Play Mode duplicate behavior.
- Actual feel of movement/camera/combat timing.
- Visual readability at target resolution.
- Teammate branch compatibility beyond these current contracts.

This document intentionally does not modify shared APIs or claim Play Mode
verification.
